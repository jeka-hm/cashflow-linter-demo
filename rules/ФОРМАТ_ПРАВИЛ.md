# Формат `rules.json`

Один файл правил для кешфлоу crm.example.com: статті, проєкти (країни) і виключення з P&L.
Його читають лінтер (закладка, скрипт для консолі, «Помічник кешфлоу») і тести. У фазі 2 його читатимуть також реєстр погоджень і `cashflow_import.js`.

## Структура файлу

```json
{
  "version": "1.2.8 (30.10.2026, корп. картку поповнюють лише з рахунку її власника)",
  "description": "…",
  "updated": "2026-10-30",
  "fix_from": "2026-09-01",
  "reference": { "articles": [ … ], "projects": { "Україна": 1, … }, "cards": [ { … } ], "card_topup": { "same_owner": true }, "counterparty_marketers": [ { … } ] },
  "people": { "mkt_zp_people": { "note": "…", "names": [ … ] } },
  "rules": [ { … }, { … } ]
}
```

### `fix_from` — межа роботи лінтера
Дата `РРРР-ММ-ДД`. Записи, датовані раніше, лінтер показує лише для довідки (статус `locked-date`) і ніколи не пропонує змінити, навіть ручною правкою. Перед самою зміною лінтер перевіряє дату ще раз на свіжих даних. Якщо поля немає, межі немає. Зараз — `2026-09-01` (уточнення 24.10.2026: перевіряємо й виправляємо з вересня 2026). Правила при цьому не змінюються: межа діє на рівні лінтера, а дати дії окремих правил — свої.

### `reference` — довідник
- `articles` — статті P&L так, як вони є в CRM: `group` (група звіту), `category` (категорія), `category_id`, `name` (стаття), `operation_id`, `type` (1 — дохід, 2 — витрата), за потреби `aliases` (інші назви).
- `projects` — проєкти (країни) з їхніми id у CRM: Україна 1, Польща 2, Велика Британія 3, США 4, ОАЕ 5. Проєкту «інші країни» в CRM немає.
- `cards` — корп. картки, яких лінтер не бачить з назви рахунку corpCard (наприклад, картку перевипустили, а назву рахунку не змінили). Поля:
  - `last4` — останні 4 цифри картки (саме так вона видна у виписці: «4246 **** **** 7365»);
  - `account_id` — рахунок corpCard у CRM, `account` — його назва (для людей);
  - `debit_account_id` — рахунок CRM, з якого картка списує (`debit_account` — для людей). Тоді corpCard звіряється разом із цим рахунком, навіть якщо покупок у виписці ще немає;
  - `holders` — хто тримає картку: `[{ "name": "Татоян Артем" }, { "from": "2026-10-23", "name": "Сидоричев Андрій" }, …]` — останній з `from` не пізніше дати покупки. Він стає маркетологом її покупок у «Звірці з банком» (маркетолог шукається в CRM за прізвищем). З 04.11.2026 тримач ще й визначає картку поповнення: погодження, в отримувачі чи тексті якого названо тримача (ім'я й прізвище, будь-який порядок і відмінок), іде на його картку («Погодження»), а переказ, записаний на іншу картку власника, «Звірка з банком» пропонує переспрямувати. Ім'я пишіть «Прізвище Ім'я», як у CRM;
  - `note` — пояснення.

  Ці картки використовують «Звірка з банком» (покупки з виписки → corpCard, маркетолог) і «Погодження» (поповнення картки за її номером → рахунок «куди»). Номер з довідника сильніший за номер у назві чи в коментарях поповнень.
- `card_topup` — на яку корп. картку можна поповнювати: `"same_owner": true` — лише на картку того самого власника, що й рахунок, з якого платять (з ФОП Хоменко — на картку Хоменка, з ТОВ — на картку цього ТОВ; уточнення 30.10.2026). Власник — з назви рахунку CRM («ФОП Прізвище …», «ТОВ НАЗВА …», «… INC.»); якщо з назви його не видно, обмеження немає. Картка без номера («майбутня корп карта …»), неактуальна чи «(видалити)» не поповнюється ніколи. Діє в «Погодженнях» (рахунок «куди», зокрема замість підказки аркуша «Корпоративні картки» реєстру; ручний вибір картки іншого власника реєстр не прийме) і в «Звірці з банком» (поповнення, записане витратою). `false` — вимкнути.

- `counterparty_marketers` — маркетолог за контрагентом: `[{ "counterparty": "Власич Оксана", "marketer_id": 195, "marketer": "Євген Сливко", "note": "…" }]`. Якщо назва контрагента є в тексті операції (отримувач, призначення; без урахування регістру й апострофів), маркетолог — цей (`marketer_id` — ID користувача CRM). Діє для статей з рекламним бюджетом: у «Звірці з банком» → «Внести в CRM» (і правила проєкту рахуються за ним, напр. «Сливко → Україна») і в «Погодженнях», якщо реєстр маркетолога не дав. Уточнення 03.11.2026: ФОП Власич Оксана Володимирівна — завжди Сливко.

Перед кожною перевіркою лінтер звіряє довідник із живим CRM (`pnl/category`, `pnl/operation/`). Якщо статтю в CRM видалили або перейменували, лінтер зупиняється ще до читання записів і показує розбіжність.

### `people` — списки імен
Варіанти написання людини, на які посилаються правила: `"names": "@mkt_zp_people"`.

## Правило

```json
{
  "id": "R-COMM-01",
  "group": "Статті",
  "title": "Банківська комісія → Комісії платіжних систем",
  "source": "ТЗ §5 (уточнення, 10.2026)",
  "priority": 100,
  "effective_from": "2024-01-01",
  "effective_to": null,
  "match":  { "type": "expense", "comment_regex": "(?i)банківськ\\w* коміс" },
  "unless": [ { "comment_regex": "(?i)\\bзп\\b|зарплат" } ],
  "set":    { "category": "Комісії платіжних систем" },
  "mode": "fix",
  "on_ambiguous": "review",
  "note": "…"
}
```

| Поле | Обов'язкове | Що означає |
|---|---|---|
| `id` | так | `R-ЛІТЕРИ-ЦИФРИ`, без повторів |
| `title` | так | назва для звіту |
| `priority` | так | число; при конфлікті перемагає більше |
| `match` | так | умова, за якої правило спрацьовує (див. «Умови») |
| `set` | так | що має бути в записі (див. «Що встановлює правило») |
| `unless` | ні | список умов-винятків: якщо спрацювала будь-яка, правило не діє |
| `effective_from`, `effective_to` | ні | дати дії, `РРРР-ММ-ДД`, обидві включно |
| `date_field` | ні | за якою датою рахувати дію: `date` (дата запису, за замовчуванням), `period` (період), `created` (коли запис внесли) |
| `mode` | ні | `fix` (за замовчуванням) або `review` — правило лише позначає записи для ручної перевірки |
| `on_ambiguous` | ні | `review` (за замовчуванням) або `skip` |
| `group`, `source`, `note` | ні | для людей: розділ, звідки правило, примітка |
| `disabled` | ні | `true` — правило вимкнено |

### Умови (`match`, `unless`, вкладені `all` / `any` / `not`)
Усі поля однієї умови мають виконуватися одночасно.

| Поле | Приклад | Пояснення |
|---|---|---|
| `comment_regex` | `"(?i)банківськ\\w* коміс"` | регулярний вираз по коментарю (див. нижче) |
| `text_any` | `["hetzner", "хостинг україна"]` | коментар містить будь-який із рядків (без урахування регістру) |
| `names` | `["Шелег*", "Турченко Адам"]` або `"@mkt_zp_people"` | у коментарі є ім'я зі списку |
| `type` | `"expense"` або `["income","expense"]` | тип запису: `income`, `expense`, `transfer`, `exchange` |
| `category_in` / `category_not_in` | `["Офіс", "Адміністративні витрати / Інші витрати"]` | поточна стаття (не) з переліку |
| `project_in` / `project_not_in` | `["Україна", null]` | поточний проєкт (не) з переліку; `null` — без проєкту |
| `account_regex` / `account_in` | `"(?i)polska"` / `[7, 8]` | рахунок за назвою / за id |
| `amount_min` / `amount_max` | `1000` | модуль суми |
| `is_manual` / `is_lead` | `true` | запис внесено вручну / створено з ліда CRM |
| `date_from` / `date_to` | `"2026-02-01"` | дата запису в межах (включно) |
| `all` / `any` / `not` | `{"any": [{…}, {…}]}` | «усі з», «будь-яка з», «не» |

Регулярні вирази пишуться як у Python: `(?i)` на початку — без урахування регістру; `\w`, `\b` враховують кирилицю (у JavaScript без перекладу вони лише латинські). Апострофи `'`, `ʼ`, `’` вважаються однаковими. Латинські літери-двійники всередині кириличних слів («Комiсiя» з латинською i) теж розпізнаються.

Імена (`names`): регістр не важливий, `*` у кінці означає «будь-яке закінчення» (`Шелег*` — Шелега, Шелеги, Шелегу). Голі імена без прізвища (наприклад, «Ігор») дають багато хибних збігів, тому в правилах вони стоять лише разом з уточненням.

### Що встановлює правило (`set`)
| Поле | Приклад | Що робить лінтер |
|---|---|---|
| `category` | `"Комісії платіжних систем"` або `"Реклама / Реінвест"` | очікувана стаття; якщо коротка назва неоднозначна (наприклад, «Інші витрати» є в кількох групах), пишіть `"Група / Стаття"` — інакше файл не пройде перевірку |
| `category_group` | `"Продукт і розробка"` | стаття має бути з цієї групи, але яка саме — не визначено → лише `review` |
| `category_not` | `["Комісії платіжних систем"]` | стаття не має бути такою, правильну визначає людина → лише `review` |
| `project` | `"США"`, `null` | очікуваний проєкт |
| `type` | `"transfer"` | має бути переказ між рахунками. Через API тип не змінюється → `review` |
| `exclude_from_pnl` | `true` | не P&L / не показувати. Видаляти записи лінтеру не можна → `review` |
| `review` | `"причина"` | лише позначити запис для ручної перевірки |

Через API лінтер змінює **тільки статтю і проєкт**. У звіт для ручної дії йде все інше:
- тип і виключення з P&L;
- статті, де CRM вимагає маркетолога (Реінвест, Дотування, Тестування, Інструменти) — як цільові, так і поточні, бо зміна зачіпає бюджет маркетолога;
- зарплатні статті (помилка 422);
- записи з кількома платежами.

## Статуси у звіті
- `ok` — запис уже відповідає правилу;
- `fix` — лінтер може виправити (після режиму редагування, резервної копії й підтвердження);
- `review` — потрібне рішення людини; застосовується лише після окремого вибору конкретного рядка;
- `manual-422` — зарплатна операція, API не дозволяє змінити (HTTP 422) → змінити вручну;
- `locked-auto` — запис з ліда CRM або автоматичний: лінтер його не змінює ніколи;
- `locked-date` — запис до межі `fix_from`: показано для довідки, лінтер його не змінює;
- `overridden` (лише в «Підсумку по правилах») — правило спрацювало, але його перекрило правило з вищим пріоритетом, яке вимагає іншого. Якщо правило з нижчим пріоритетом хоче те саме, що й переможець (наприклад, «джуни → Дослідження» і «Сливко → Дослідження»), воно має той самий статус, що й переможець.

Конфлікти: якщо два правила вимагають різного для одного поля, перемагає вищий `priority`. При рівному пріоритеті запис іде в `review`. Якщо в лінтері вибрано лише частину правил, пріоритети все одно рахуються за всіма. Тоді невибране правило з вищим пріоритетом не обійдеться: такий запис буде `review`.

## Як змінити правило
1. Відредагуйте `rules/rules.json` (кодування UTF-8). Додайте або змініть випадки в `test/rule-cases.json`: для кожного правила потрібен хоча б один позитивний (`pos`) і один негативний (`neg`) випадок, для правил з датами дії — межі (`date`).
2. Перевірте файл:
   - у «Помічнику кешфлоу» відкрийте вкладку «Правила»: там видно помилки й є поле «Перевірити коментар»;
   - або запустіть тести: `tools\node\node.exe --test test\*.test.js`.
3. Для «Помічника» досить закрити й знову відкрити програму. Для закладки перезберіть її подвійним кліком на `build\Зібрати закладки.bat` (або `python build\build.py`) і заново перетягніть кнопку зі сторінки `dist\встановлення.html`: правила вшиті в закладку.
4. Перший запуск зі зміненими правилами — завжди перегляд (dry-run).
