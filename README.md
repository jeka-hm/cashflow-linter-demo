# Лінтер кешфлоу

Панель для бухгалтера. Вона звіряє виписки банків із записами кешфлоу в CRM і показує, що не сходиться.

> Це публічна версія робочого проєкту. Усі назви, люди, рахунки й суми в ній — вигадані.

## Яку проблему розв'язує

У компанії є кілька фірм і ФОП, рахунки в ПриватБанку й monobank, корпоративні картки. Кожну операцію банку треба мати в кешфлоу CRM: з правильною сумою, датою, рахунком і статтею. Вручну це сотні рядків щомісяця. Банк і CRM записують те саме по-різному: банк зараховує оплату без комісії, CRM — повністю; банк платить податки двома платежами, CRM розносить їх по людях. Тому просте порівняння «рядок до рядка» показує сотні хибних розбіжностей. Лінтер знає ці відмінності й лишає людині тільки справжні питання.

## Що вміє

- **Звіряє залишки й обороти** кожного рахунку: банк проти CRM, за день або за місяць.
- **Пояснює різницю.** Показує, якої операції немає в CRM, а якого запису немає в банку.
- **Розпізнає «записано інакше».** Перекази між своїми рахунками, продаж валюти, LiqPay (сума без комісії), покупки карткою з іншою датою, податки із зарплати по людях, платіж і його повернення.
- **Пропонує створити запис.** Статтю бере з правил або з історії рахунку. Запис іде в чернетки CRM — проводить його людина.
- **Знаходить записи з не тим типом.** Наприклад, поповнення картки, записане витратою. Пропонує змінити на переказ.
- **Перевіряє статті й проєкти** за правилами з файлу `rules/rules.json`. Правила можна читати й змінювати без програміста.
- **Перевіряє, чи можна закривати місяць.**

Виписки бере локальна програма «Помічник» через офіційні API ПриватБанку й monobank. Токени банків лишаються на комп'ютері бухгалтера.

## Демо

Відкрити в браузері: **https://jeka-hm.github.io/cashflow-linter-demo/**

Демо працює без сервера. CRM і банки в ньому імітує скрипт у самій сторінці. Дані вигадані.

## Як запустити в себе (Windows)

Потрібні [Node.js](https://nodejs.org) 22 або новіший і Python 3.10 або новіший. Команди — з папки проєкту.

Тести:

```powershell
node --test "test/*.test.js"
pip install requests
python -m unittest discover -s test -p "test_*.py"
```

Має вийти: 514 тестів JavaScript і 93 тести Python, усі зелені.

Збірка панелі в папку `dist\` (будь-яка з двох команд, результат однаковий):

```powershell
node build\build.js
python build\build.py
```

Демо на своєму комп'ютері:

```powershell
node build\build-demo.js
python -m http.server 8000 --directory docs
```

Далі відкрити `http://localhost:8000/` і натиснути «Відкрити панель».

Є ще тестовий сервер, який імітує CRM для ручної перевірки закладки:

```powershell
node test\e2e\make_e2e.js
python -I test\mock_crm_server.py --static work\e2e --bank work\e2e\bank_test.json
```

Сторінка — `http://127.0.0.1:8899/e2e/index.html`.

## Як зроблено: людина + ШІ

Я фінансист, який автоматизує власну роботу. Кешфлоу я веду щодня, тому знаю задачу зсередини. Цей інструмент я спроєктував і довів до робочого стану сам, а код писав у парі з ШІ-асистентом Claude Code. Пишу про це прямо: поставити задачу ШІ так, щоб результат можна було перевірити, зібрати з цього робочу систему й утримати якість — це і є моя інженерна частина.

**Моя частина:**

- Задачі — зі щоденної роботи. Наприклад: «лінтер показує 260 операцій, яких нібито немає в CRM, а більшість там є».
- Правила обліку простими словами. Що вважати переказом, що доходом, у який місяць відносити зарплату.
- Перевірка кожної зміни на справжніх виписках і записах. Не «тести зелені», а «цифри зійшлися з банком».
- Помилки, знайдені очима. Наприклад: погодження однієї людини прив'язалось до виплати її однофамільця.
- Рішення. Що робити автоматично, а що лишати людині. Де потрібна кнопка, а де досить підказки.
- Будова системи. Правила — окремим файлом, який читається без програміста. Записи з виписки — спершу чернетками. Токени банків — лише на комп'ютері бухгалтера. Панель за замовчуванням нічого не змінює.
- Керування роботою ШІ. Розбиття великої задачі на кроки, порядок «тест → виправлення → перевірка на даних», запуск оглядів кількома агентами, рішення, які знахідки приймати.
- Інтеграції. Підключення API ПриватБанку й monobank, Google Apps Script для таблиці погоджень, Claude API для підказок — з лімітами витрат.

**Частина ШІ-асистента:**

- Код і тести.
- Розбір виписок: чому не сходиться і як це розпізнати.
- Огляди коду кількома агентами одночасно. Кожен агент шукає помилки під своїм кутом: гроші й дати, безпека, записи в CRM, зручність.

**Правила, яких ми трималися:**

- **Спершу тест, потім виправлення.** Кожну помилку спочатку відтворює тест, який падає на старому коді. Потім код виправляється.
- **Огляди колами.** Приклади: 10 агентів — 30 знахідок, усі виправлено. 18 агентів і ще 7 на перевірку — 40 виправлень. 8 агентів — 40 знахідок: 7 виправлено одразу, ще 17 пунктів — наступним кроком, кожен з тестом.
- **Помірність.** Сто агентів за раз — дорого й не краще. Добре працюють 10–20.
- **Лінтер нічого не змінює сам.** Зміни — тільки кнопкою людини, після резервної копії. За замовчуванням панель відкривається лише для перегляду.
- **Суми — як у банку.** Лінтер не «підганяє» цифри. Якщо не сходиться, він каже, де саме.
- **Помилки ШІ — теж у журналі.** Одного разу рядок, що лишився після правки, зламав передачу даних. Після цього з'явились правило «перечитати весь diff перед здачею» і тест, який шукає неоголошені змінні.

Що це дало мені: уміння поставити задачу так, щоб її можна було перевірити, і довести інструмент від ідеї до щоденного використання. І звичку не вірити результату, поки не побачу його на своїх даних.

## Результати в цифрах

- Проєкт зроблено приблизно за чотири тижні, близько 70 кроків «задача → перевірка → виправлення».
- У цій версії 514 тестів JavaScript і 93 тести Python. У робочій версії, разом з частинами, яких тут немає, — близько 540 і 110.
- Один справжній місяць: операцій банку «без запису в CRM» панель спершу показувала 262. Після того як звірка навчилась розпізнавати «записано інакше», лишилось 83. Після подальших правил і внесених записів — 25. Це вже справжні питання, а не шум.
- Вивантаження виписок усіх фірм за місяць — близько двох хвилин замість ручного збирання файлів.

## Що не ввійшло в публічну версію

- **Вкладка «Погодження».** Вона вбудовує сторонню програму — реєстр погоджень виплат. Це чужий код, тому його тут немає. Допоміжний код вкладки лишився (`ui/approvals-tab.js`) і тестується, але сама вкладка в цій збірці схована.
- **Скрипт Google-таблиці** з реєстром погоджень — він про внутрішні таблиці компанії.
- **Справжні правила й дані.** `rules/rules.json` тут — демонстраційний: структура і логіка справжні, а прізвища, назви фірм, номери рахунків, карток і тарифи замінено на вигадані. Те саме — у тестах.
- **Встановлення й оновлення** в колег, підпис робочим ключем. Тут збірка підписується демонстраційним ключем, який створюється під час першої збірки.
- **Внутрішні документи:** інструкція користувача, журнал змін, відкриті питання.

Тексти в коді подекуди згадують ці частини («Оновити.bat», «реєстр погоджень»). Це сліди робочої версії.

## English summary

**Cashflow Linter** is a browser panel (a bookmarklet) for an accountant. It reconciles bank statements (PrivatBank and monobank APIs) with cash-flow records in a company CRM.
It compares balances and turnovers per account and explains every difference.
It understands cases where the bank and the CRM record the same event differently: own transfers, currency sale, LiqPay net amount plus fee, card purchases posted later, payroll taxes per person, refunds.
It proposes missing records as CRM drafts, proposes fixes for records with a wrong type, and checks categories and projects against rules in `rules/rules.json`.
A small local Python helper fetches the statements; bank tokens never leave the accountant's computer.
The repository has 514 JavaScript tests and 93 Python tests, and a serverless demo in `docs/` with synthetic data.
I am a finance specialist, not a programmer. I designed the requirements from my daily work, verified every change on real statements and made the decisions.
The code and tests were written together with an AI assistant (Claude Code), including multi-agent code reviews and a strict "failing test first" rule.
This public copy contains no real company or personal data: names, accounts, amounts and tariffs are fictional.
Not included: the third-party approvals registry integration, the real rules, and internal documents.
